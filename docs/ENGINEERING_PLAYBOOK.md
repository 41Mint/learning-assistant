# 生成式软件工程工作约定

本项目既是学习助手，也是实践 AI Coding 与软件工程能力的长期载体。AI 的价值不只在于更快生成代码，还在于帮助把问题变成可验证、可维护、可演化的软件。

## 核心原则

1. **意图、规格、实现分离**：先明确用户真正要解决的问题（Intention），再定义可验收的行为（Specification），最后讨论组件、状态和代码（Implementation）。不能因为实现简单而跳过前两步。
2. **最小正确闭环优先**：每次只完成一个能被用户使用和验证的最小增量；不为假设中的未来需求提前堆叠架构或功能。
3. **确定性优先**：涉及数据计算、存储迁移、导入导出和状态转换时，优先由可测试的确定性代码处理；AI 生成内容只作为辅助，不作为唯一事实来源。
4. **证据而非“看起来完成”**：功能完成至少要有构建检查，并针对关键流程做与需求对应的验证；已知限制和未验证项必须记录。
5. **可维护性是交付的一部分**：保持职责清晰、类型完整、命名可读、数据源一致；避免硬编码、临时补丁和无说明的重复逻辑。
6. **把一次探索沉淀下来**：稳定的设计决策、踩坑和验证路径写入项目文档，减少下一次从零理解的成本。

## 每项功能的交付流程

### 1. Intention：澄清目标

在编码前用简短文字明确：

- 用户要解决的场景与预期收益；
- 本次范围与明确不做的内容；
- 成功的可观察结果。

### 2. Specification：定义可验收行为

为功能列出少量可验证的验收条件，包括：正常流程、关键边界/异常、数据如何保存或保持兼容。需求不明确且会改变产品行为时，先由用户决策；其余可逆的实现细节由 Agent 说明后推进。

### 3. Implementation：选择最小实现

在现有架构内说明拟修改的模块、数据流和风险。优先复用已有组件、store 与依赖；新增依赖、LocalStorage 数据迁移、显著 UI/交互路线变化、远程推送或不可逆操作，必须先说明影响并取得用户确认。

### 4. Build：小步实现

按可运行的垂直切片实现，避免在未验证核心流程前并行堆积大量功能。临时方案必须标为 `HACK` 或 `TODO`，并说明后续处理条件。

### 5. Verify：用证据验证

- 运行与改动匹配的构建、静态检查或测试；
- 将关键验收条件逐项对应到验证结果；
- 若无法自动验证，明确需要用户手测的步骤和原因。

### 6. Record：形成可追溯交付

- 将组员可见的变更写入[更新日志](../CHANGELOG.md)。操作变化同步到对应的使用指南或验收步骤。
- 在[待办事项](./TODO.md)维护后续工作。影响长期维护的取舍记入相应的架构或交互约定。
- 记录重要决策、已知限制与后续工作；
- 以一个可理解、可回退的本地 Git commit 收束功能。推送远程仓库前由用户确认。

## 文档职责与事实优先级

以当前代码和验收结果核对实现，以更新日志追溯交付，以待办事项确认优先级。README 提供本地启动和文档入口。早期记录保留在[归档目录](./archive)。

## 协作约定

- 开发或修改前端交互时，参照[前端样式与交互约定](./FRONTEND_GUIDE.md)复用现有组件和主题变量。
- 新功能的入口优先放在当前任务或资料旁。入门引导优先直接打开对应操作。验证空工作区和已有资料时各自能否找到下一步。
- 扩展已有工作流前，先核对同类操作的入口、打开和返回方式。多个入口共用相同的任务面板，智能体工具优先在窗口内完成操作，只有查看原资料或进入编辑表单时才按用户所选动作导航。
- 新增删除或移出类确认时，复用同模块已有的页面内弹窗，保持确认、取消与 Esc 的行为一致。
- 聊天输入框的快捷问题共用横向列表，保持单行排列，空间不足时可左右滚动。
- 用户负责意图、优先级与影响体验的取舍；Agent 负责分析、实现、验证与解释。
- 用户想借开发学习 Git 时，Agent 会在执行关键 Git 操作前说明目的、作用范围和是否改变历史。
- 不提供密码、令牌等凭据；连接 GitHub 时仅需用户自行授权或提供仓库地址。
